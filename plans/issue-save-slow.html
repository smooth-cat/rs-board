保存截图后，为什么讲义列表要等约 4 秒才出现新条目？

RS Board 保存链路图解 · 原图 / 预览图的编解码路径 · 讲义列表更新逻辑  （依据当前代码，行号均指向 crates/app/src/）
一句话结论：点保存后，截图文件（原图 PNG + manifest）在几百毫秒内就已落盘，UI 也已切回讲义窗口； 但讲义列表读的是内存缓存 recent.documents，而这次缓存刷新被排在 post-save 串行任务链的最后——必须等「解码原图 → 全分辨率合成 → 缩出预览图 → 编码预览 → 安装预览 → 全库扫描」 全部跑完才执行。高分辨率（4K/8K）下这条链要约 4 秒，列表在新条目出现前一直显示旧数据。

0参与保存的线程角色

UI 线程（egui） background-png-encode 预编码线程 save worker（保存工作线程） post-save-coordinator（单线程，串行）

前三个各自独立；post-save-coordinator 是保存完成后唯一的后台通道，剪贴板复制、预览图生成、列表刷新全部挤在它一条线程上排队执行 （post_save.rs:146-249，单 worker 循环取任务）。

哪些编解码阻塞主线程（UI 线程）

保存路径全程不阻塞主线程——预编码、落盘、post-save 链（解码原图 / 合成 / 预览 / 剪贴板 / 保存后的扫描）都在后台线程， 代价只是「列表更新晚 4 秒」，界面不会卡。真正卡界面的是下面三处与「打开 / 显示 / 扫库」相关的同步解码：

三处主线程解码的细节：
① 打开讲义双重解码——worker 线程加载文档时已把原图整体解码过一次（仅为校验尺寸，store.rs:806）， 结果回到 UI 线程后 session_from_loaded 又用 CGImageSource 把同一份 PNG 解码成 CGImage（application.rs:847）。 打开一份讲义 = 原图解码两次，其中一次在主线程。编辑器背景展示本身不再耗 CPU： CGImage 直接挂到 CALayer 呈现（capture_surface.rs:654-657），开销集中在构建 CGImage 那一刻。
② 库操作后的全库扫描在主线程——只有「保存后」那次扫描走 post-save 线程；启动（application.rs:302） 与导入/改名/删除/导出/清空之后的 recent.refresh（1059, 1442, 1454, 1465） 都是在 UI 线程同步调用 scan_documents：库里 N 份讲义就在主线程解码 N 张全分辨率原图，讲义越多窗口冻结越久。
③ 缩略图解码——每份讲义首次出现（或预览路径变化）时在 UI 线程解码一次 ≤480px 预览图并上传纹理，之后命中缓存，影响很小。

保存路径的等待链（当前实现的因果图）

# 用户感知的等待 = 下列所有步骤串行完成 点击保存 └→ 快照 + 落盘（原图 PNG 字节搬运 + manifest） ← 此刻文件已可用 └→ UI 切回讲义窗口（显示旧缓存） └→ post-save 单线程，按 next_work() 优先级取任务： 1. 剪贴板队列（若开启：需先解码原图+全分辨率合成，再 PNG+TIFF 双编码） 2. 渲染/预览：解码原图 → 全分辨率合成 → 缩 480px → 编码预览 → 安装（再解码原图） 3. recent_refresh：scan_documents（逐份解码原图） ← 列表数据此刻才产生 └→ apply_scan → 讲义列表出现新条目（≈点击后 4s）

5可优化的方向（供讨论）

  • 落盘即更新列表（收益最大、改动最小）：在 WorkerEvent::Save 成功分支直接用本次保存的 snapshot 信息对 recent.documents 做 upsert（新条目先占位、无缩略图），不再等 post-save 链。需处理 preview_path 暂缺（缩略图后补）。application.rs:1344-1414
  • 解耦列表刷新与图片任务：让 recent_refresh 不等预览生成（并行或提前），预览装好后单独补一次缩略图纹理刷新。post_save.rs:118-137
  • 让扫描不再解码原图：scan_documents 只读 manifest（标题/时间/preview_revision + 预览文件存在性检查即可），去掉 load_managed_package 里对背景 PNG 的读取与 decode_rgba8()。store.rs:804-806
